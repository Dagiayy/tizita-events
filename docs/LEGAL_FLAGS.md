# Legal and regulatory decisions flagged for Ethiopian counsel

This is a technical implementation. It implements the **controls** the specification requires and keeps every legal parameter configurable. It does **not** interpret Ethiopian law. The items below must be validated before launch; until then the code labels the affected content as draft and ships safe, adjustable defaults.

| # | Topic (spec ref) | What the software does | Decision needed / where to change |
|---|---|---|---|
| L1 | **Retention default** 180 days after closure (D31) | Configurable per plan (`plans.retention_days`), per add-on, and platform default (`retention.default_days` / `RETENTION_DEFAULT_DAYS`). Not hard-coded. | Counsel to approve the schedule; adjust plans/settings. |
| L2 | **Deletion grace** 7–30 days (D32) | Clamped to 7–30, default 14 (`deletion.grace_days`). | Approve window and wording of the deletion policy. |
| L3 | **Backup retention / erasure in backups** (D33, R9) | Backups expire after `BACKUP_RETENTION_DAYS` (35); each deletion job records `backup_purge_by`; DR runbook re-runs completed deletions after a restore. | Approve backup period and whether deleted data persisting in expiring backups is acceptable. |
| L4 | **Rights-request response time** | `rights.sla_days` (default 30) sets `due_at`, overdue flag in admin. The value is a placeholder, not a legal conclusion. | Counsel to set the statutory response period. |
| L5 | **Consent text** for guests (§9.2) | Separate active consent action before upload, recorded with policy version, locale, session, timestamp; withdrawal supported. Notice text is a **draft** (`legal_status = draft_pending_legal_review`, shown in the UI as "draft"). | Approve/replace the guest notice (en + am) and set `legal_status='approved'` through a migration/admin update. |
| L6 | **Privacy policy, Terms, Host terms/DPA, content & copyright policy, refund policy** (§13.1) | Placeholder rows in `policy_documents` flagged draft. Documents themselves are not authored here. | Counsel to draft and approve all documents listed in spec 13.1. |
| L7 | **Controller / processor allocation** between platform and host (D54) | Not decided in code. Host owns event purpose; platform provides tooling. | Formal legal review before production. |
| L8 | **Registration with the supervisory authority; DPO decision** (§9.3, D53) | Out of scope for software. Compliance owner needed from launch. | Register as required; document DPO decision before scale. |
| L9 | **Minors** (PDPP Art. 11) | No separate minor profiles, no face/biometric processing; removal flow exists. | Counsel to confirm obligations for incidental minors in event photos and guardian handling. |
| L10 | **Biometrics / face matching** | **Not implemented**, no embeddings stored anywhere (D08). | Re-open only with DPIA + legal approval. |
| L11 | **Cross-border transfers & vendors** (§9.4, D27–D29, D43, D50) | `assertProductionSafety` blocks foreign-cloud endpoints; vendor register with `outside_ethiopia`; a vendor outside Ethiopia cannot be activated without DPA + transfer assessment reference. No image AI, no foreign CDN, no push vendor. Guests outside Ethiopia can still open links (D17/D19). | Complete the register (SMS, payment, hosting) with real contract data; assess any future vendor. |
| L12 | **Breach notification** 72 h (§9.5) | Incident records with explicit *discovered at* time, regulator/subject due times, overdue indicators, evidence log. | Approve notification templates and contact list; named incident commander. |
| L13 | **Audit-log retention** | Audit events are append-only and never auto-deleted. | Decide retention period and whether/when archival or minimisation is required. |
| L14 | **Data-subject access report** contents | Staff can generate a JSON report of what is held for a guest session or user. | Confirm required scope/format. |
| L15 | **VAT / TOT, e-invoicing, cash-register** (§12.3, D57) | Invoices carry `tax_status='unvalidated'`; `tax.vat_rate` is `null` until the accountant sets it; invoice numbering uses a database sequence (**gaps are possible after rollbacks — confirm whether gapless numbering is required**). | Accountant/authority confirmation before charging customers. |
| L16 | **Payments licensing** (§12.1) | Only licensed gateways (Chapa, telebirr-ready); no stored value, no custody of host funds, no card/wallet data. | Confirm provider terms (fees, refunds, data location, settlement). |
| L17 | **Copyright / content licence** (D65) | Hosts/uploaders warrant rights through the notice; platform licence limited to operating the service. | Counsel to finalise licence language. |
| L18 | **Law-enforcement requests / criminal content** (§9.6) | Escalation flow (`escalated` reports, `criminal_content` incident kind, audited elevated access, legal hold). | Define the procedure and who may authorise disclosure. |
| L19 | **Cookies / tracking notice** (§13.1) | Web analytics are first-party aggregates; no third-party scripts; refresh cookie is strictly necessary. | Confirm whether a notice is still required. |
| L20 | **IP/device logs retention** (§9.1) | IPs hashed for guests; raw IP stored for staff sessions and audit; no retention job yet. | Define retention periods for security logs and add a purge job if required. |
| L21 | **Sender names shown to other guests** (gallery "People" view) | Only the display name a guest typed on the join screen is shown (never phone numbers or ids); keys are opaque per-event hashes; the owner can switch it off (`show_uploader_names`, Settings) and the API then returns no names/keys. Default is **on**. | Counsel to confirm the default and whether the join screen needs a line telling guests their name is visible to other guests of the event. |

Status values `draft_pending_legal_review` / `unvalidated` in the database and UI are intentional markers; they are removed only by an explicit, audited change after counsel/accountant sign-off.
